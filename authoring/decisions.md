# Decision register

Settled decisions are not reopened. Open decisions are resolved only when they block the current phase, at a review gate. Record new questions in the relevant status file.

## Identity and delivery

- Name: **ggbrick**; domain target ggbrick.design; npm scope `@ggbrick`; prefix `ggb-` for CSS classes (`ggb-<id>`, `ggb-<id>__<part>`), theme attributes (`data-ggb-*`) and custom properties (`--ggb-*`). `gg-` was rejected as too common; `ggb-` is short and collision-free. Skills are named `ggb-*`.
- Three deliverables from the same sources: Figma library, Svelte 5 package on Bits UI, documentation (local Markdown shipped with the package, and a site).
- Distribution: the npm package is the tested unit. Consumers may also copy a component's source folder into their project or download the whole `packages/svelte` source; every component folder is therefore self-contained (see AGENTS.md). No compatibility with any third-party registry or CLI is pursued. Bits UI is the only runtime dependency allowed besides Svelte. shadcn-svelte may be consulted as an implementation reference, never as a dependency or a format.
- Two Astro apps deployed on their own domains: `apps/docs` (Starlight at the root, docs.ggbrick.design, reading `documentation/` and embedding live Svelte examples) and `apps/site` (marketing, ggbrick.design). Both consume `@ggbrick/svelte` and `@ggbrick/tokens`; shared navigation lives as design-system components. A single app with docs under a sub-path was considered and rejected: a sub-domain needs no base path or host rewrites (2026-09-26).
- Hosting: Cloudflare Workers with static assets, built and deployed by Workers Builds (Cloudflare's Git integration): every branch except the production one gets a preview URL, no deployment token in GitHub. `apps/docs/wrangler.jsonc` configures docs.ggbrick.design; the marketing site will follow the same model (user decision, 2026-10-15).
- The production branch of the sites is `release`, not `main`: the Deliver procedure merges the released revision of `main` into `release`, so docs.ggbrick.design always matches the published package and publishing the site stays an explicit, versioned act. `release` is created at the first Deliver; until then the site exists only as branch previews (user decision, 2026-10-15).
- Phase 1 delivers the design system (foundations, components, Figma library, docs, marketing site). Phase 2 delivers the theme builder (a web form producing a brand overlay) and the Figma import (plugin and/or Claude skill). The overlay format is the sparse brand folder already defined by the token architecture.
- Versioning proposal (adopt at first Deliver): semantic versioning, one version shared by tokens, Svelte package and Figma library; 0.x while the catalog grows.
- License: MIT for the code (user, 2026-11-18, before the repository became public): `LICENSE` at the root and a `license` field in every manifest. Third-party material copied into the repository (the Phosphor paths) is listed with its notice in `THIRD-PARTY-NOTICES.md`; keep that file current when copying anything else. The packed packages ship them: `npm run generate` copies both into `packages/svelte` and the license into `packages/tokens` (ignored copies, like the other consumer copies), and CI checks the packed Svelte package. The license of the Figma library is still open.
- The repository is public and read-only for outsiders (user, 2026-11-18): no outside issues or pull requests for now, as `CONTRIBUTING.md` says; security reports go through GitHub private vulnerability reporting (`SECURITY.md`). Everything committed is public, with its history: no secret, and no personal data beyond the GitHub handle (no real name, e-mail address or account identifier) in files, commit messages or pull request text.

## Sources and tokens

- `foundations/` holds the sources of truth and nothing else: `foundations/tokens/` (DTCG tokens with their `config.json`, `inventory.json`, `palette.config.json` and `status.json`; approved at the tokens review) and `foundations/components/<family>/<id>/` (contract, status and Figma specification of each component). A `components/` folder at the root was misleading, since it promised implementations; those live in `packages/svelte/src/components/<id>/`, and the Figma library has one page per component named by its path (`actions/button`). The same hierarchy therefore appears in the sources, the package and Figma (user decision, 2026-10-13).
- The repository owns DTCG JSON tokens and compact JSON component contracts. Figma, code and documentation derive from or conform to them.
- Generated CSS is layered like the sources: base primitives/common under `[data-ggb-brand]`, appearance roles under `[data-ggb-appearance]`, density roles under `[data-ggb-density]`, sparse brand overrides under combined selectors; aliases become `var()` references. `foundations/tokens/config.json` names a default appearance and density (light, standard): the base block applies under `:root, [data-ggb-brand]` with the default appearance and density roles, so a document without attributes, or with a brand attribute alone, is usable. Appearance and density can be overridden alone in a subtree. A brand switch in a subtree gets the defaults unless it restates appearance and density on the same element, because a custom property substitutes its `var()` references on the element that declares it and descendants inherit the computed value (foundations change, 2026-10-13; the earlier claim that any attribute could be overridden alone was wrong for brand).
- Token layers: primitives, semantic, and component tokens only where justified. Primitives are **generous**: full ramps and scales are defined up front so that semantic roles pick from them; unused primitives are expected (see `authoring/foundations.md`).
- **Semantic role or component token** (user decisions, 2026-11-01 and 2026-11-03, at the wave 3 contract gate; the naming rule confirmed by the user on 2026-11-03 after review of its application: "Ok pour le 1 alors, on mets ça en place"). Where a token lives is read from its name, so that nobody needs to know which components use it. A **component token** is named by the component it belongs to, `component.<id>.<name>` (the track size of a switch, `component.switch.track-size.md`), in `foundations/tokens/base/components/<id>.tokens.json` (brand overrides in `foundations/tokens/<brand>/components/<id>.tokens.json`), emitted as `--ggb-component-<id>-…` in `tokens.css` and as `component/<id>/…` in the Figma Brand collection; only that component's contract binds it. A **semantic role** is named by what it describes in the interface, a family and a role (`color.surface.overlay`, `size.control.md`, `color.input.focus.border`), never by a component: if the natural name of a value needs a component name, it is a component token. A component id may appear in a semantic name only when that word is a general concept the role describes for every component, declared under `concepts` in `foundations/tokens/inventory.json` with its reason (icon, link, and the levels toast and tooltip of the `layer.*` scale, which is read as a whole). A component token cannot vary by density (a value that follows density is a semantic role, as the Button spacing decided on 2026-09-27), and no component token merely renames a semantic role: the contract's token roles already do that. `tooling/check-foundations.ts` enforces both sides: component token files, paths and ownership, and semantic names that contain a component id without a declared concept. Applied on 2026-11-01 and 2026-11-03: `size.switch.*` became `component.switch.track-size.*`; the wave 3 values for Progress, Spinner, Tooltip and Dialog were created as component tokens; `color.field.*` became `color.input.*` (the family paints text entry boxes, not the Field component); `size.avatar.*` was removed and its values recorded for the Avatar contract (`authoring/component-catalog.md`). Figma variables were renamed in place (IDs and bindings kept).
- Base is complete and usable alone. Brands are sparse overrides with matching file names and token paths. Every brand supports light and dark by inheritance or explicit values.
- Brand, appearance (light/dark) and density (compact/standard/comfortable) are independent axes selected on one ancestor. No viewport token axis: layout chooses composition; it does not rewrite token values.
- Precedence: base primitives, brand primitives, base common, base appearance, base density, base components, brand common, brand appearance, brand density, brand components. Aliases resolve after merging.
- Spacing families: layout, content and control. Visible dimensions are distinct from interaction targets. Minimum interaction target 44 × 44 CSS px.
- Font and icon sizes do not shrink with density; spacing and control heights do.
- Color primitives are generated in OKLCH from `foundations/tokens/palette.config.json` (one lightness per step index across hues). The semantic layer starts with `color.palette.{neutral,accent,info,success,warning,danger}.<step>`, six ramps aliasing primitive ramps; every color role references a palette ramp, so a brand changes an accent with eleven aliases. This is the brand overlay format the theme builder produces (foundations review, 2026-09-26).
- Fonts: Inter for interface text in every brand, IBM Plex Mono for code roles (foundations review, 2026-09-26).
- Figma variable collections mirror the token layers: Primitives (single mode, every primitive shared by all brands), Brand, Appearance and Density (modes from `foundations/tokens/config.json`; the default mode of each collection is the config default: base, light, standard). A primitive a brand overrides moves to Brand with one value per brand mode (an explicit migration). Component tokens live in Brand under `component/<id>/…`, since they vary by brand at most and a separate collection would duplicate the brand modes. Variable values mirror the source aliases (foundations review, 2026-09-26).
- Icons: Phosphor Icons (MIT) is the reference set. ggbrick bundles no icon set: slot content receives icons from the application in `currentColor`; the few intrinsic glyphs a component needs (chevron, check, close…) are inline SVG paths copied into the component folder, attributed to Phosphor, and overridable through a snippet prop. Figma masters use the Phosphor community library through instance-swap properties (foundations review, 2026-09-26). Amended on 2026-10-19 (user, wave 1 IconButton, Link and Badge): the community library is not available to the file, so Phosphor 2.1.1 regular (1,512 glyphs, from `@phosphor-icons/core`) is imported into the library file as local components `phosphor/<name>` on the page `assets/phosphor`, with a notes frame (import record, usage, updating). Designers choose glyphs only through the Icon component (its Glyph property) or a component's icon slot, never by inserting a `phosphor/…` component directly. Ledger: `reports/assets/phosphor/ledger.json`.

## Contracts and implementation

- A contract has `id`, `props` (enum, boolean, string, number; `bindable` for two-way values), `parts` (with slot cardinality), `states`, optional `events`, `tokens`, `rules` (format in `authoring/contract-format.md`). Intrinsic behavior lives in rules; platform mechanics stay in adapters. Figma and code must offer corresponding options; a Figma boolean need not become a variant.
- Token roles use parameterized paths; enum props become `data-*` selectors, enum states become custom-property suffixes in generated CSS; role types follow the naming convention.
- Svelte 5 with runes and snippets; Bits UI primitives for native semantics; CSS inheritance and `currentColor` for slot content; logical CSS properties; `prefers-reduced-motion` and `forced-colors` handled in every component with motion or borders. Prettier and ESLint enforce formatting and lint rules across sessions.
- Snippet slots cannot statically enforce component identity; allowed content is a contract rule documented in usage docs.
- Every component stylesheet (handwritten `<id>.css` and generated `tokens.generated.css`) is wrapped in the cascade layer `@layer ggb`, so that an application's unlayered rule overrides a component declaration whatever the selector specificity (a generated `.ggb-button[data-intent][data-appearance]` selector has specificity 0,3,0). `tokens.css` stays unlayered. Decided on 2026-10-31 (audit, lot 1); the browser suite checks that computed values are unchanged.

- The whole repository is TypeScript: components and package in strict TypeScript, tooling and tests in TypeScript executed natively by Node (type stripping, Node 22.18 or newer, erasable syntax only: no enums, namespaces or parameter properties). Shared tooling types live in `tooling/lib/types.ts`. No build step for scripts.

## Documentation

- One maintained source per component in `documentation/components/<id>.md`, sections in this order: Overview, Anatomy, When to use, When not to use, Best practices, Examples, API, Accessibility. The page answers what the component is, when to use it, when not to, and how to use it well, concisely: a one- or two-sentence overview, short When to use and When not to use lists, and Best practices as a table (Guidance, Topic, Practice; all Do rows, then all Don't rows, without forcing pairs) rendered as a card with badges on the site (user review of the docs site, 2026-10-15). Contracts, approvals and evidence stay out of the page: they ship as `contracts/<id>.json`, live in status files and reports, and are explained in `documentation/foundations/contracts.md`, so that agents reading a component page are not distracted. `documentation/index.json` is the economical agent index.
- Foundations guides live in `documentation/foundations/` (overview, color, typography, spacing, shape, elevation, motion), are listed under `foundations` in `documentation/index.json` and ship in the package: for each role, what it is for, plus rules, so that agents style what components do not cover with the right roles. Values stay out of the Markdown; the site shows them per context (user decision, 2026-10-15).
- Examples that can run on their own are ` ```svelte live ` blocks of the Markdown page: the documentation site compiles and renders each one above its code, so the Markdown stays the single source and the site build verifies the examples. The site is Starlight dressed in ggbrick tokens with brand and density selects beside the light/dark one, and adds Getting started pages and Foundations pages generated from the resolved tokens (user choices at the start of the site task, 2026-10-14). Each component page opens with a playground (the component in a card, key options as selects in its corners) and shows the Figma blueprint boards under Anatomy; the generated contract and evidence section was removed at the site review (2026-10-15).
- **Progressive detail** (user, 2026-11-06, session https://claude.ai/code/session_0156c543GZBnpgBmqmSNfDLB: "Le but de la documentation à priori c'est de dire aux designers/dev et IA : Voilà la liste des composants, et voilà la recette de comment et quand utiliser chaque"). Three levels: `index.json` to choose a component, its page for how and when to use it, its contract (`contracts/<id>.json`) only when the technical detail is needed. Anatomy lists the parts in usage terms, numbered like the blueprint, with no token names, measurements or colors, and ends with one line pointing to the contract; the pages name a token only where the reader acts on it.
- Introduce a component by its user-facing purpose; framework names and native mappings belong in API. Accessibility lists relevant WCAG 2.2 criteria with level, link and the component/integration split; listing is not a conformance claim.
- Figma specification sections: Overview, Anatomy, Variants, States, Behavior & sizing, Usage examples. Masters are distinguished from explanatory instances.
- Figma specification pages are support for designers working in Figma, never a source for agents: an agent learns a component from its contract, `documentation/` (the package's `docs/`) and the implementation, and never reads the specification frames, nor Figma Specs (Markdown blocks on the canvas), for component facts. Specifications stay frames; Figma Specs are not adopted (user decision, 2026-10-30).
- Derived semantic roles maintained by hand per brand or density (`radius.focus`, `space.control.padding-inline`) are declared as `invariants` in `foundations/tokens/inventory.json` and checked in every context by `tooling/check-foundations.ts` (2026-10-13).

## Branches and delivery to production

- `main` is production: what it contains is released or releasable. Nothing is committed to it directly.
- Every task runs on its own branch created from `main`: `component/<id>`, `wave/<n>`, `foundations/<topic>`, `docs/<topic>`, `site/<topic>`, `fix/<topic>`, `chore/<topic>`. A session works and pushes on its branch as often as it likes; commits are not PRs.
- A pull request to `main` is opened when a unit of work is complete: a component that meets the definition of Done (or whose only pending gate is Figma parity, stated in the PR), an approved foundations change, a finished site task, a fix. The PR follows `.github/pull_request_template.md`, CI must be green, and the user merges it. Merge commits, no force-push on shared branches.
- GitHub branch protection on `main` (PR required, CI required) is configured by the user in the repository settings.

## Process

- Lifecycle: scope, contract, implementation, implementation review, Figma parity, documentation, delivery. Gates: tokens review (once per tokens change), then per component contract, interactive implementation (which is the design review) and Figma parity; delivery approval is separate. Implementation precedes Figma because tokens fix the visual language and the reviewer judges the real rendering; Figma then reproduces validated, measurable values (decided 2026-09-25).
- Waves group components so gates are batched (see roadmap). Modify reopens only affected gates. Audit is read-only. Figma reconciliation and foundation changes belong to Modify.
- Done means usable in Figma and code with accessible, version-aligned human and agent documentation and recorded evidence.
- Figma is operated through the Figma MCP server. Reconstruction scripts are Plugin API bodies written per task (reusable ones kept in `authoring/adapters/figma`); IDs are read from the destination file, never guessed. Skills in `.claude/skills` are the executable procedures; `authoring/workflows/*.md` hold the rationale and checks.
- Figma masters are configured from their properties only (variants, booleans, text, exposed nested instances): adapter variable modes are set by the variants themselves, never chosen by a designer on an instance (user, 2026-10-20, at the Figma parity review of Link).
- A component that shows an icon imposes its size: its Figma master places the Phosphor glyph instance directly (bound to the size it imposes) behind an instance-swap property of its own, and never nests the Icon component, whose Size would show on the instance (user, 2026-10-26, at the wave 1 Figma parity review). Icon is the component for an icon on its own. An instance-swap property has one default for the whole set. The same holds for the components a host holds: inside a host, Counter and Shortcut are replaced by the internal parts `_Counter/Nested` and `_Shortcut/Nested`, sized by the host's Components mode and without Size; Counter and Shortcut keep their Size for use on their own (user, 2026-10-26).
- The pre-ggbrick reference kit (tag `reference-kit-2026-09` (commit cd0a2a2, always reachable in the branch history)) is a model of artifact structure only. ggbrick starts from zero, Button included, so that everything is unified.

## Overlays, composition and shared code (pre-wave 3, 2026-10-31)

Decided by the user point by point in the Claude Code session https://claude.ai/code/session_0156c5459xsSFh6jdvshCSsu, from the audit `reports/audits/2026-10-31-etat-des-lieux.md`. Two of them carry a condition stated in their entry.

- **Overlays use the browser top layer, not a portal.** Dialog and Drawer render a native `<dialog>` opened with `showModal()`; Popover, Menu, Tooltip, Select and Combobox panels carry the `popover` attribute. The content stays in the DOM subtree that opens it, so it inherits `data-ggb-brand`, `data-ggb-appearance` and `data-ggb-density` by the cascade; nested overlays stack in opening order; light dismiss, Escape, the inert background and the modal focus trap come from the platform. Bits UI stays the base for roles and keyboard behavior (menus, listboxes, tabs) with its portal disabled; where a Bits UI primitive assumes its own portal or focus management, ggbrick writes its own overlay primitive in `packages/svelte/src/lib/` (see the shared-code decision below). Positioning uses CSS anchor positioning with a JavaScript fallback where support is missing. Alternatives rejected: a Bits UI portal to `body` with the theme attributes copied onto the portalled content (runtime code in every overlay, a z-index scale to maintain); a portal to the nearest themed ancestor (clipped by overflow and transforms); theme attributes on `<html>` only (loses subtree overrides, needed by the theme builder preview). **Validated** on 2026-11-01: the spike (`examples/spike-overlays/`, `tests/browser/spike-overlays.spec.ts`, findings in `reports/spikes/2026-10-31-overlays.md`) passed in Chromium with both positioning engines and the user confirmed the decision (session https://claude.ai/code/session_0156c5459xsSFh6jdvshCSsu). Firefox and WebKit smoke projects are due before the first overlay implementation gate.
- **The `layer.*` scale is kept and redocumented.** `layer.raised` and `layer.sticky` serve elements that stay in the flow; `layer.dropdown`, `layer.overlay`, `layer.modal`, `layer.tooltip` and `layer.toast` become the fallback for an overlay whose top layer promotion is disabled per instance. No token is removed. Rejected: shrinking the scale (removal of approved tokens, Figma resync, no fallback left).
- **Elevation in the dark appearance is carried by an elevation border.** A new role `color.elevation.border`, transparent in light and visible in dark (a neutral step chosen at the tokens review), is drawn by raised and floating surfaces in addition to their shadow; surfaces and shadows stay as approved. Rejected: lightening `color.surface.raised` in dark (merges with overlay, jumps two steps on the canvas); shadows per appearance (little visible effect on a dark background). **Approved** on 2026-11-01 on the foundations review page (`color.elevation.border` neutral.700 in dark), together with `color.item.*` and `motion.distance.*`; the visual pass before the first release (roadmap 4b) may revisit the values.
- **Selected and highlighted items get one family, `color.item`.** Conditions default, hover, selected, selected-hover and disabled, each with surface, content and border, plus `color.item.indicator` (active tab bar, chosen item mark). It serves Menu, Select, Combobox, Tabs, Pagination, Toolbar and later SegmentedControl. Rejected: a `selected` condition on `color.action` (27 more triplets, an item is neither an intent nor an appearance); reusing `action.neutral.ghost.hover` and `color.selection` (text selection and item selection would be tied for a brand).
- **Compound components are one contract with a `children` block.** The parent contract declares its named children (`item`, `separator`, `group`…) with their props, states, tokens and rules; `build:svelte` generates the bindings of each child from that contract; Figma reproduces them as internal parts (`_Menu/Item`). One contract, one status, one gate per compound component. The schema also gains a `records` prop type (a list of objects with declared fields, for Select and Combobox options and Table rows) and an optional `contrast` block listing the role pairs to measure, since the generic check only knows `surface`, `content`, `border` and `focusColor`. The RadioGroup/Radio pair stays as built. Rejected: one contract per exported component (about forty contracts and statuses for waves 3 and 4); items as data only (loses free content per item). The schema extension is reviewed before the first wave 3 contract.
- **A child of a compound component is a unit** (user, 2026-11-04, session https://claude.ai/code/session_0156c543GZBnpgBmqmSNfDLB: "Chaque toast est un composant unitaire qui ne dépend que d'elle même, la seule limite est en effet qu'elle doit être placé dans une toastRegion"). Its generated token bindings sit on its own class (`.ggb-toast__item`, `.ggb-menu__item`) and depend only on its own props and on the theme around it (brand, appearance, density); a role is scoped under the parent only if its template reads a parent prop (none does today). Where a child must be placed (a Toast in a ToastRegion, a MenuItem in a Menu) is a usage rule of the contract, not a styling dependency. Before, every child was scoped under its parent, so a Toast outside a region lost its tokens.
- **Shared code lives in `packages/svelte/src/lib/`, in copyable modules.** The exception `authoring/architecture.md` reserved is activated: a few modules typed once (`field-context`, `overlay` for the top layer, `visually-hidden.css`…). Each component status declares the modules it uses under `dependencies`, the copy rule becomes "the component folder plus the listed modules", and `build:svelte` checks that the declaration matches the real imports. Rejected: generating the shared pieces into every folder (duplicated, heavier, harder to debug); controlled manual copies.
- **Overlay motion is CSS only.** Entry through `@starting-style`, exit through `transition-behavior: allow-discrete`, on `:popover-open` and `[open]`, with `motion.duration.*`, `motion.easing.enter` and `motion.easing.exit`, plus two distance roles to add (`motion.distance.sm`, `motion.distance.md`) for the offset. Under reduced motion the overlay fades without moving. The rule is written once here and repeated verbatim in every overlay contract. Rejected: Svelte transitions with `forceMount` (JavaScript-driven, a second mechanism, incompatible with the native popover toggle without a wrapper); no motion until the visual pass (tokens and the reduced-motion rule would be retrofitted into approved contracts).

- **Modal backdrop: `color.surface.scrim`** (user, 2026-11-03, wave 3 contract gate: "ok (meme si le wording scrim n'est pas très parlant...)"). The dimming layer behind a modal window (Dialog, later Drawer) is painted with `color.surface.scrim`, which already carries its transparency. `opacity.scrim` stays for a veil an application builds from another color (over an image or a video) and is not used by overlays. The user finds the word scrim unclear: the foundations guides explain it in plain words; a rename is not decided. Rejected: `opacity.scrim` over a surface color (two tokens for one effect).
- **Contract versus Bits UI** (user, 2026-11-03, wave 3 contract gate: "Ok"). When a Bits UI behavior disagrees with a contract rule, the contract wins: the component overrides or completes the primitive locally, as RadioGroup does, pins the Bits UI version in its status and covers the override with a browser test, so that an upgrade that changes the behavior fails a test instead of drifting silently. Rejected: adapting the contract to the primitive (the contract is platform independent).
