# Figma operating mode

Figma is the validated visual representation of ggbrick. It is operated through the **Figma MCP server** connected to the session. Inspect the tools it exposes at session start (reading design context and screenshots, and executing Plugin API code in the file) and follow the server's own instructions or skill; nothing here replaces them.

## Model

- One ggbrick library file. Pages, in order: Cover, Getting started, Foundations; the library pages, one per family (`Actions`, `Content`, `Forms`, `Feedback`, `Overlays` since 2026-11-03…), opening with an overview frame (`<Family> — Overview`: description, an isometric cover of live instances in several brands and appearances, one card per component linking to its section and its specification) and holding the masters, one section per component named after it, headed by a `Section header` (name, summary, specification link, internal parts note, properties read from the set) above the component set and its internal parts (`_<Name>/…`, packed on its right), followed by the asset pages `assets/<name>` holding imported libraries that components consume (`assets/phosphor`: the Phosphor glyphs behind Icon, with a notes frame; designers reach them only through components); then one page per component named by its repository path (`forms/checkbox`) holding its specification frame and the explanatory instances, with links at the top right of the title row (Master, then Documentation and Contract once published); and Utilities (documentation tooling `_Spec/*`, prefixed `_`; review fixtures `_Fixture/*` when a component needs a stand-in; the stored script libraries `_Script/spec-lib` and `_Script/family-pages`, hidden and locked, since 2026-11-03). Separator pages (`---`) split the groups. The Assets panel groups the masters by library page, then by section. Decided by the user on 2026-10-29 (component pages had held the masters since 2026-10-13); scripts find masters by their component set ID from the ledger, never by page, and a new master goes to its family page in a section of its own (`authoring/adapters/figma/library-pages.plugin.js`, then `family-pages.plugin.js` and `spec-header-links.plugin.js`; overview and section headers since 2026-10-30, user request).
- Variables: collections **Foundations · Primitives** (single mode `default`), **Foundations · Brand**, **Foundations · Appearance** and **Foundations · Density**, the last three with exactly the modes of `foundations/tokens/config.json` (the code and these documents call them by their axis, Primitives, Brand, Appearance, Density; the prefix makes the flat, alphabetical collection list read as two families next to the hidden `Components` collections); each collection's default mode is the config default (base, light, standard), set by the sync script through `setDefaultMode`, so a node without explicit modes resolves like a document without `data-ggb-*` attributes. Primitives shared by every brand live in Primitives; a primitive a brand overrides is emitted in Brand with one value per brand; component tokens go to Brand under `component/<id>/…` (a separate collection would duplicate the brand modes). The generated `packages/tokens/figma-manifest.json` is the source of variable names, types, scopes, WEB code syntax and values; values mirror the source aliases (an Appearance role aliases the Brand palette variable it references), so the chain reads in Figma as in the token files; opacity tokens are the one conversion: Figma reads a number bound to layer opacity as a percentage, so `opacity.*`, `primitive.opacity.*` and component tokens named after an opacity (`component.spinner.track-opacity`) are emitted ×100 (0.7 → 70). `figma-expectations.json` holds the expected resolved values per brand and mode pair. Typography roles become text styles whose family, weight, size and letter spacing are bound to the role's variables (`typography/<role>/fontFamily|fontWeight|fontSize|letterSpacing`, aliases of the `primitive/font/*` variables) and whose line height is typed as a percentage (`primitive/font/lineHeight/*` and `typography/<role>/lineHeightRatio` are percentage strings: Figma cannot bind a percentage); shadows become effect styles. Component adapter variables (`button/…`, `counter/…`, `shortcut/…`, `badge/…`) live in one hidden collection `Components` (modes sm, md, lg), plus `Components · button style` and `Components · button state` for the Button's two mode axes (reused by the IconButton), `Components · action family` (modes default, neutral, info, success, warning, danger; since 2026-11-03) through which an Alert or an intense Toast points the accent and neutral buttons it holds at the action family of its intent, and `Components · link size` and `Components · link color`, whose modes stand for the font and the color of the text around a Link (Figma has no inheritance; each Link variant sets them on itself, so designers choose variants, never modes: user decision of 2026-10-20). `npm run figma:batches` writes the ready-to-run scripts (`dist/figma/variables-<n>.js`, `styles.js`, `verify.js`) from the adapter bodies in `authoring/adapters/figma/`; run them in order through `use_figma`, then `npm run figma:check -- <result.json>` writes `reports/tokens/figma/verification.json`. The library file key and the collection, mode and variable IDs are recorded in `reports/tokens/figma/ledger.json`.
- Component masters are built per contract: enum props become variant properties or booleans by meaning (do not multiply variants for optional children), parts become named layers, slot parts become instance-swap properties limited to compatible fixtures, tokens become variable bindings. Explanatory instances live in specification frames, not inside the master set.
- Record every node ID the design system owns in `reports/components/<id>/figma/ledger.json` (masters, variant sets, fixtures, specification frames) and the file key in the component status. Never guess an ID; read it from the file.

## Procedure for a component (ggb-component, parity phase)

1. Read the contract, the approved implementation, its computed-value report (`reports/components/<id>/svelte/computed.json`) and `authoring/templates/figma-specification.md`.
2. Inspect the destination: existing pages, variables, masters and the ledger. Reuse existing fixtures and variables.
3. Build masters with the Plugin API through the MCP code-execution tool, in small batches you verify visually (screenshot) after each batch. Preserve existing IDs. Bind every visual property to a variable; no hard-coded colors or sizes in masters.
4. Build the specification page: Overview, Anatomy, Variants, States, Behavior & sizing, Usage examples, with explanatory instances of the master.
5. Verify parity: Figma resolution against the computed values for every option and state in each brand and mode pair; public property exposure on the master; difficult cases (long labels, empty optional slots, constrained width, all states in light and dark). Write `reports/components/<id>/figma/parity.json`.
6. Present the parity review with file and node links, screenshots and the parity report. Stop for the Figma parity gate.

The kit's own script bodies stay readable at tag `reference-kit-2026-09`; scripts for ggbrick are written per task and, when reusable, kept in that folder.

## One file

The library is one Figma file holding the foundations (token collections, text and effect styles) and the components (masters, parts, specifications, adapter collections). A separate tokens library was considered and rejected on 2026-10-14 (user decision): a community or client distribution needs a self-contained file, since a duplicate outside the team loses its links to an external library, and a split would add a publication step before every component build. The two levels are kept apart by naming: `Foundations · …` collections for the tokens, `Components…` for the adapter variables, `Wireframe` for the documentation tooling, the last two hidden from publishing.

## Publication

Publishing the library, its access and its versioning are Deliver decisions requiring explicit authorization. The user decided on 2026-10-19 that the first publication includes the Phosphor glyphs of `assets/phosphor` (needed by the Glyph swap in other files); how designers use them is reviewed after tests in a consuming file.
